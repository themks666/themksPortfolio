# Next.js: The Complete Guide to Building Modern Web Applications

Next.js is a React framework for building modern, production-ready web applications.

It extends React with features that are commonly required when building complete applications, including:

* File-based routing
* Nested layouts
* Server Components
* Client Components
* Server-side rendering
* Static generation
* Dynamic rendering
* Data fetching
* Caching
* Server Actions
* API endpoints
* Dynamic routes
* Middleware and request interception
* Image optimization
* Font optimization
* Metadata and SEO
* Error handling
* Loading states
* Authentication patterns
* Database integration
* Full-stack application development
* Production deployment

Instead of combining React with many separate libraries and configuration files, Next.js provides an opinionated application structure that allows developers to build both the frontend and backend parts of an application in the same project.

This guide starts with the fundamentals and gradually moves toward advanced Next.js concepts.

# What Is Next.js?

Next.js is a framework built on top of React.

React provides the tools for creating user interfaces, while Next.js adds application-level features.

A traditional React application may require additional libraries for:

* Routing
* SEO
* Server-side rendering
* API development
* Image optimization
* Font optimization
* Data fetching
* Application structure
* Deployment
* Backend integration

Next.js provides solutions for many of these requirements directly inside the framework.

A simplified React application might look like this:

```jsx
function App() {
  return (
    <main>
      <h1>Hello World</h1>
    </main>
  );
}

export default App;
```

A Next.js application can use the same React components while also providing routing, layouts, server rendering, API routes, and many other features.

# Why Use Next.js?

Next.js is popular because it allows developers to build complete applications rather than only isolated user interfaces.

## 1. File-Based Routing

Routes can be created by creating files and folders.

```text
app/
├── page.jsx
├── about/
│   └── page.jsx
└── contact/
    └── page.jsx
```

This produces:

```text
/
/about
/contact
```

No separate router configuration is required.

---

## 2. Server Components

Next.js uses React Server Components by default in the App Router.

This allows components to execute on the server and send only the required UI to the browser.

---

## 3. Client Components

Interactive components can be converted into Client Components when browser-side JavaScript is required.

```jsx
"use client";

import { useState } from "react";

export default function Counter() {
  const [count, setCount] = useState(0);

  return (
    <button onClick={() => setCount(count + 1)}>
      Count: {count}
    </button>
  );
}
```

---

## 4. Full-Stack Development

Next.js can contain both frontend and backend functionality.

For example:

```text
Next.js Application
│
├── UI
├── Pages
├── Components
├── Server Components
├── Server Actions
├── API Routes
└── Database
```

This makes Next.js suitable for applications such as:

* Blogs
* E-commerce websites
* Dashboards
* Social media platforms
* SaaS applications
* Portfolio websites
* Admin panels
* Content management systems

# Next.js vs React

React and Next.js are not direct competitors.

React is a UI library.

Next.js is a framework built around React.

| Feature             | React                             | Next.js                 |
| ------------------- | --------------------------------- | ----------------------- |
| UI Components       | Yes                               | Yes                     |
| Routing             | External library usually required | Built in                |
| Server Components   | React feature                     | First-class integration |
| API Routes          | No                                | Yes                     |
| Server Rendering    | Requires setup/framework          | Built in                |
| Static Generation   | Requires setup/framework          | Built in                |
| Image Optimization  | External solution                 | Built in                |
| Metadata APIs       | External/manual                   | Built in                |
| Full-Stack Features | Limited                           | Yes                     |

A useful way to think about it is:

```text
React
  ↓
User Interface

Next.js
  ↓
React
  +
Routing
  +
Server Rendering
  +
Backend Features
  +
Optimization
  +
Deployment
```

# Pages and Routes

A `page.tsx` file represents a route.

Example:

```tsx
export default function HomePage() {
  return (
    <main>
      <h1>Welcome to my website</h1>
    </main>
  );
}
```

The file:

```text
app/page.tsx
```

represents:

```text
/
```

Now create:

```text
app/about/page.tsx
```

```tsx
export default function AboutPage() {
  return (
    <main>
      <h1>About Me</h1>
      <p>This is my about page.</p>
    </main>
  );
}
```

This creates:

```text
/about
```

# Layouts

Layouts allow you to share UI between multiple pages.

The root layout is:

```text
app/layout.tsx
```

Example:

```tsx
export default function RootLayout({
  children,
}: {
  children: React.ReactNode;
}) {
  return (
    <html lang="en">
      <body>
        <header>
          <nav>
            <a href="/">Home</a>
            <a href="/about">About</a>
          </nav>
        </header>

        {children}

        <footer>
          <p>© 2026 My Website</p>
        </footer>
      </body>
    </html>
  );
}
```

The `children` represents the current page.

For example:

```text
RootLayout
│
├── Header
│
├── Current Page
│
└── Footer
```

# Nested Layouts

Layouts can also be nested.

Consider:

```text
app/
├── layout.tsx
├── page.tsx
└── dashboard/
    ├── layout.tsx
    ├── page.tsx
    └── settings/
        └── page.tsx
```

The dashboard layout can contain a sidebar.

```tsx
export default function DashboardLayout({
  children,
}: {
  children: React.ReactNode;
}) {
  return (
    <section className="dashboard">
      <aside>
        <nav>
          <a href="/dashboard">Dashboard</a>
          <a href="/dashboard/settings">Settings</a>
        </nav>
      </aside>

      <main>{children}</main>
    </section>
  );
}
```

Both dashboard pages will use this layout.

# Dynamic Routes

Dynamic routes are useful when the URL contains a variable value.

For example:

```text
/blog/hello-nextjs
/blog/learn-react
/blog/nextjs-server-components
```

Create:

```text
app/blog/[slug]/page.tsx
```

Then:

```tsx
export default async function BlogPost({
  params,
}: {
  params: Promise<{ slug: string }>;
}) {
  const { slug } = await params;

  return (
    <main>
      <h1>Blog Post</h1>
      <p>Slug: {slug}</p>
    </main>
  );
}
```

Visiting:

```text
/blog/hello-nextjs
```

gives:

```text
hello-nextjs
```

as the `slug`.

---

# Dynamic Routes With Data

Dynamic routes become especially useful when retrieving data.

```tsx
const posts = {
  "nextjs-guide": {
    title: "Complete Next.js Guide",
    content: "Learn Next.js from beginner to advanced.",
  },
  "react-guide": {
    title: "React Guide",
    content: "Learn React fundamentals.",
  },
};

export default async function PostPage({
  params,
}: {
  params: Promise<{ slug: string }>;
}) {
  const { slug } = await params;

  const post = posts[slug as keyof typeof posts];

  if (!post) {
    return <h1>Post not found</h1>;
  }

  return (
    <article>
      <h1>{post.title}</h1>
      <p>{post.content}</p>
    </article>
  );
}
```

# Catch-All Routes

A catch-all route uses:

```text
[...slug]
```

Example:

```text
app/docs/[...slug]/page.tsx
```

It can match:

```text
/docs/react
/docs/react/hooks
/docs/react/hooks/use-state
```

Example:

```tsx
export default async function DocsPage({
  params,
}: {
  params: Promise<{ slug: string[] }>;
}) {
  const { slug } = await params;

  return (
    <main>
      <h1>Documentation</h1>

      <p>{slug.join(" / ")}</p>
    </main>
  );
}
```

# Route Groups

Route groups allow you to organize routes without changing the URL.

Create:

```text
app/
├── (marketing)/
│   ├── about/
│   │   └── page.tsx
│   └── pricing/
│       └── page.tsx
│
└── (dashboard)/
    └── dashboard/
        └── page.tsx
```

The parentheses indicate that the folder is a route group.

The URL for:

```text
app/(marketing)/about/page.tsx
```

is still:

```text
/about
```

The `(marketing)` part is not included in the URL.

# Server Components

Server Components are a major part of modern Next.js.

Components inside the App Router are Server Components by default.

Example:

```tsx
export default async function UsersPage() {
  const response = await fetch(
    "https://api.example.com/users"
  );

  const users = await response.json();

  return (
    <main>
      <h1>Users</h1>

      {users.map((user: any) => (
        <div key={user.id}>
          {user.name}
        </div>
      ))}
    </main>
  );
}
```

This component can execute on the server.

---

# Advantages of Server Components

Server Components can be useful because they:

* Reduce client-side JavaScript
* Can access server-side resources
* Can query databases directly
* Keep secrets away from the browser
* Can perform server-side data fetching
* Improve initial rendering strategies

For example, database credentials should never be exposed to the browser.

A Server Component can communicate with the database on the server.

```text
Browser
   │
   ▼
Next.js Server
   │
   ▼
Database
```

Instead of:

```text
Browser
   │
   ▼
Database
```

which would expose credentials and create security problems.

---

# Client Components

Server Components cannot directly use browser-specific features such as:

* `useState`
* `useEffect`
* `useRef`
* Browser event handlers
* Certain browser APIs

When you need these features, use a Client Component.

```tsx
"use client";

import { useState } from "react";

export default function Counter() {
  const [count, setCount] = useState(0);

  return (
    <button onClick={() => setCount(count + 1)}>
      Count: {count}
    </button>
  );
}
```

The `"use client"` directive tells Next.js that this component should run on the client.

---

# When to Use Client Components

Use Client Components when you need:

```text
useState
useEffect
useReducer
useRef
onClick
onChange
onSubmit
Browser APIs
Interactive UI
```

For example:

```tsx
"use client";

import { useState } from "react";

export default function SearchBox() {
  const [query, setQuery] = useState("");

  return (
    <input
      value={query}
      onChange={(event) => setQuery(event.target.value)}
      placeholder="Search..."
    />
  );
}
```

---

# Server vs Client Components

A useful rule is:

```text
Server Component
    ↓
Data fetching
Database access
Sensitive operations
Static UI

Client Component
    ↓
State
Events
Browser APIs
Interactive UI
```

Avoid turning the entire application into Client Components unnecessarily.

Instead, keep most of the application on the server and introduce Client Components only where interaction requires them.

# Fetching Data

Next.js allows Server Components to fetch data directly.

```tsx
export default async function ProductsPage() {
  const response = await fetch(
    "https://api.example.com/products"
  );

  const products = await response.json();

  return (
    <main>
      <h1>Products</h1>

      {products.map((product: any) => (
        <article key={product.id}>
          <h2>{product.name}</h2>
          <p>${product.price}</p>
        </article>
      ))}
    </main>
  );
}
```

Because the component is asynchronous, it can wait for the data before rendering.

---

# Fetching Data From an API

Suppose your API returns:

```json
[
  {
    "id": 1,
    "name": "Laptop"
  },
  {
    "id": 2,
    "name": "Keyboard"
  }
]
```

You can fetch it like:

```tsx
async function getProducts() {
  const response = await fetch(
    "https://api.example.com/products"
  );

  if (!response.ok) {
    throw new Error("Failed to fetch products");
  }

  return response.json();
}

export default async function ProductsPage() {
  const products = await getProducts();

  return (
    <main>
      {products.map((product: any) => (
        <div key={product.id}>
          {product.name}
        </div>
      ))}
    </main>
  );
}
```

Always check whether a request succeeded when appropriate.

# Fetching Data From a Database

One major benefit of Server Components is that server-only code can stay on the server.

For example, suppose you have a database utility:

```ts
import { prisma } from "@/lib/prisma";

export async function getUsers() {
  return prisma.user.findMany();
}
```

Then:

```tsx
import { getUsers } from "@/lib/users";

export default async function UsersPage() {
  const users = await getUsers();

  return (
    <main>
      <h1>Users</h1>

      {users.map((user) => (
        <div key={user.id}>
          {user.name}
        </div>
      ))}
    </main>
  );
}
```

The browser does not need to receive your database credentials.

# Error Handling

Next.js supports special error files.

Create:

```text
app/
└── dashboard/
    ├── error.tsx
    └── page.tsx
```

Because error components need interactivity, they are Client Components.

```tsx
"use client";

export default function Error({
  reset,
}: {
  error: Error & { digest?: string };
  reset: () => void;
}) {
  return (
    <div>
      <h2>Something went wrong.</h2>

      <button onClick={() => reset()}>
        Try again
      </button>
    </div>
  );
}
```

The `reset()` function can attempt to render the affected route again.

# Not Found Pages

You can create:

```text
app/not-found.tsx
```

Example:

```tsx
export default function NotFound() {
  return (
    <main>
      <h1>404</h1>
      <p>The page you are looking for does not exist.</p>
    </main>
  );
}
```

For dynamic routes, you can use `notFound()`.

```tsx
import { notFound } from "next/navigation";

export default async function PostPage({
  params,
}: {
  params: Promise<{ slug: string }>;
}) {
  const { slug } = await params;

  const post = await getPost(slug);

  if (!post) {
    notFound();
  }

  return (
    <article>
      <h1>{post.title}</h1>
    </article>
  );
}
```

# Metadata and SEO

Next.js provides a metadata API.

Static metadata:

```tsx
import type { Metadata } from "next";

export const metadata: Metadata = {
  title: "My Blog",
  description: "A blog built with Next.js",
};

export default function HomePage() {
  return <h1>My Blog</h1>;
}
```

You can also define metadata dynamically.

```tsx
import type { Metadata } from "next";

export async function generateMetadata({
  params,
}: {
  params: Promise<{ slug: string }>;
}): Promise<Metadata> {
  const { slug } = await params;

  const post = await getPost(slug);

  return {
    title: post.title,
    description: post.description,
  };
}
```

This is particularly useful for blogs and e-commerce applications.

# Environment Variables

Environment variables are useful for storing configuration and secrets.

Create:

```text
.env.local
```

Example:

```env
DATABASE_URL="your-database-url"
JWT_SECRET="your-secret"
API_URL="https://api.example.com"
```

Server-side variables can be accessed using:

```ts
const databaseUrl = process.env.DATABASE_URL;
```

Variables intended to be exposed to browser code generally use:

```env
NEXT_PUBLIC_API_URL="https://api.example.com"
```

Do not place secrets inside `NEXT_PUBLIC_*` variables.

For example, this is dangerous:

```env
NEXT_PUBLIC_DATABASE_PASSWORD="secret"
```

Public environment variables can be included in client-side code.

# POST Route Handler

```ts
import { NextResponse } from "next/server";

export async function POST(request: Request) {
  const body = await request.json();

  return NextResponse.json({
    message: "User created",
    user: body,
  });
}
```

A client could send:

# Authentication

Authentication determines who a user is.

A typical authentication system looks like:

```text
User
 │
 ▼
Login Form
 │
 ▼
Server
 │
 ├── Validate credentials
 │
 ├── Create session
 │
 └── Set secure cookie
 │
 ▼
Authenticated User
```

A login route could look like:

```ts
import { NextResponse } from "next/server";

export async function POST(request: Request) {
  const { email, password } = await request.json();

  const user = await authenticateUser(
    email,
    password
  );

  if (!user) {
    return NextResponse.json(
      { error: "Invalid credentials" },
      { status: 401 }
    );
  }

  const response = NextResponse.json({
    message: "Login successful",
  });

  response.cookies.set("session", "session-token", {
    httpOnly: true,
    secure: process.env.NODE_ENV === "production",
    sameSite: "lax",
    path: "/",
  });

  return response;
}
```

In a real application, use a proper authentication/session library or a carefully designed server-side session system rather than storing passwords or sensitive data in client-side storage.

# Revalidation

Revalidation allows data to be refreshed after a period of time.

For example:

```tsx
const response = await fetch(
```

This expresses a desire to reuse the fetched result and refresh it periodically.

This pattern can be useful for content that does not need to change on every request.

Examples:

```text

Products

Documentation
```

# Middleware and Request Interception

Next.js supports request interception through its request-processing features. In current Next.js versions, this functionality may be represented through the `proxy.ts` convention depending on the version and project setup.

A common use case is checking authentication before allowing access to certain routes.

Conceptually:

```text
Request
   │
   ▼
Request Interception
   │
   ├── Authenticated → Continue
   │
   └── Not authenticated → Redirect
```

For example, the logic might look like:

```ts
import { NextResponse } from "next/server";

export function proxy(request: Request) {
  const authenticated = true;

  if (!authenticated) {
    return NextResponse.redirect(
      new URL("/login", request.url)
    );
  }

  return NextResponse.next();
}
```

The exact API and file convention should be checked against the Next.js version used by your project.

# Pagination

Suppose your URL is:

```text

```

You can retrieve the page number:

```tsx
export default async function ProductsPage({
  searchParams,
```

```ts

  skip,
  take: pageSize,
```

# Parallel Data Fetching

If two pieces of data are independent, they can often be fetched in parallel.

Instead of:

```tsx
const users = await getUsers();

const posts = await getPosts();
```

you can use:

```tsx
const [users, posts] = await Promise.all([
  getUsers(),
  getPosts(),
]);
```

This can reduce total waiting time.

Conceptually:

```text
Sequential

Request
  │
  ▼
Users
  │
  ▼
Posts
  │
  ▼
Response
```

versus:

```text
Parallel

        ┌── Users ──┐
Request ┤           ├── Response
        └── Posts ──┘
```

# Sequential Data Fetching

Sometimes requests depend on each other.

For example:

```tsx
const user = await getUser();

const posts = await getPostsByUser(user.id);
```

Here, the second request requires the result of the first.

Therefore sequential fetching is appropriate.

# Security Considerations

Full-stack frameworks make it easier to build applications, but security is still the developer's responsibility.

## Never expose secrets

Bad:

```tsx
"use client";

const secret = process.env.DATABASE_PASSWORD;
```

Never expose database passwords, private API keys, or authentication secrets to browser code.

---

## Validate user input

Do not trust incoming data.

For example:

```ts
const title = String(formData.get("title") ?? "");

if (title.length < 3) {
  throw new Error("Title is too short");
}
```

For larger applications, use a validation library such as Zod.

Example:

```ts
import { z } from "zod";

const postSchema = z.object({
  title: z.string().min(3),
  content: z.string().min(10),
});

const result = postSchema.safeParse({
  title,
  content,
});

if (!result.success) {
  throw new Error("Invalid post data");
}
```

# Authentication Security

```ts
  secure: true,
  sameSite: "lax",
  path: "/"
```

```tsx
  await connectDB();

  const posts = await Post.find()
    .sort({ createdAt: -1 })
    .lean();

  return (
    <main>
      {posts.map((post: any) => (
        <article key={post._id.toString()}>
          <h2>{post.title}</h2>
          <p>{post.content}</p>
        </article>
      ))}
    </main>
  );
}
```

This makes Next.js a strong option for developers already familiar with MERN.

# A Complete CRUD Example

A typical application needs CRUD operations:

```text
Create
Read
Update
Delete
```

Suppose we have a todo application.

## Create

```ts
"use server";

export async function createTodo(formData: FormData) {
  const title = String(
    formData.get("title") ?? ""
  );

  if (!title.trim()) {
    throw new Error("Title is required");
  }

  await db.todo.create({
    data: {
      title,
    },
  });
}
```

## Read

```tsx
export default async function TodoPage() {
  const todos = await db.todo.findMany();

  return (
    <main>
      {todos.map((todo) => (
        <div key={todo.id}>
          {todo.title}
        </div>
      ))}
    </main>
  );
}
```

## Update

```ts
"use server";

export async function updateTodo(
  id: string,
  title: string
) {
  await db.todo.update({
    where: {
      id,
    },
    data: {
      title,
    },
  });
}
```

## Delete

```ts
"use server";

export async function deleteTodo(id: string) {
  await db.todo.delete({
    where: {
      id,
    },
  });
}
```

This is the foundation of many CRUD applications.

# The Most Important Mental Model

One of the most important things to understand about modern Next.js is that your application is not simply:

```text
React → Browser
```

Instead, think of it as:

```text
                         Next.js
                            │
              ┌─────────────┴─────────────┐
              │                           │
           Server                       Client
              │                           │
      ┌───────┼────────┐          ┌───────┼───────┐
      │       │        │          │       │       │
   Database  APIs   Server      State   Events  Browser
                     Actions
```

The server is responsible for server-side work.

The client is responsible for browser interaction.

Learning when to use each side is one of the most important skills in modern Next.js development.
